# Poda — current-state audit

Read-only audit. No code or data was changed, no migrations were run, and the live database was not queried.
Audience: another assistant that will plan changes from this diagnostic.

## 1. Executive summary

- Stack: a static multi-page site (hand-written HTML, one CSS file, vanilla JS) with no framework or router. Supabase provides Postgres, Auth and Storage. A small Cloudflare Worker (_worker.js) handles three /api/* routes and sends mail through Resend. The note editor is Tiptap, prebuilt into poda-editor.bundle.js.
- Production vs local:
  - Production matches commit 4fcedbb: it has the 5-folder homepage and the Archive page, and no Lookbook tile.
  - The local checkout is ahead of production, with uncommitted changes (section 10).
- Two release systems exist side by side.
  - The legacy one: drops, items, studies and notes are JSON rows ({id, data jsonb}). home.html, item.html and the old Edit grid still use it.
  - The new one is relational: edits (folders), edit_placements, products, suppliers and folder_updates. The homepage and folder pages use it.
- A folder is an `edits` row. There is no "current folder" flag. The public site derives the current folder: the live one first, otherwise the newest open one.
- Admin: a single page (admin.html, admin.js) with 15 views and a password-only login. The folder workspace is Edits -> open a folder. It has a details form, a status dropdown, product placement, text updates, and attach/detach for notes and studies.
- Missing in the folder admin: no folder delete, no placement reorder, no editorial-copy UI, no folder preview, no image upload for updates.
- Notes: a full editor with autosave, and only draft and published states. Editing an already-published note autosaves straight to the live site after 4 seconds.
- Lookbook (Visual Studies): images are pasted as URLs only, with no upload UI. Studies have no draft state and are public the moment they exist.
- Access control (from the SQL in the repo; not checked against the database): several legacy tables are world-readable or writable by any signed-in user. Hiding is done in the interface only. Details in section 8.
- Draft folders: a draft folder does not hide a published note attached to it from the Inbox.
- Scheduling is manual. publish_at is only a display label, and there is no scheduler.
- Email: it only goes out from the admin "Send" action on a note. Publishing a note or a folder sends nothing.
- Database state is unverified. The owner reported running the setup SQL and hitting errors. Whether FOLDERS_PUBLIC_SETUP.sql is applied is unknown.

## 4. Current folder workflow

1. Create. Edits -> "+ New Edit". The title is entered in a browser prompt(). The row is created as draft, with the number, standfirst and date empty.
2. Details. The builder opens with a form for folder number, drop date, title and standfirst, plus a status dropdown (draft, scheduled, live, archived). The details form needs "Save details". The status dropdown saves the moment you change it.
3. Products. The left column lists accepted, unplaced products with "+ Add to folder". The right column lists the placements. There is only a Remove button, and new placements are appended at the end.
4. Updates. "+ New update" uses a browser prompt() for text. New updates are unpublished by default. The only actions are Publish/Unpublish and Delete. There is no text edit and no image, even though the table has an image_path column.
5. Notes and studies. Published notes and all studies are listed with Attach/Detach. An attachment is a single value stored inside the note or study record, so each can belong to one folder only.
6. Release. Set the status to scheduled to open the folder publicly (notes, imagery and published updates show; the product grid stays locked). Set it to live to reveal the products. Set it to archived to move it to the Archive page.
7. Missing: delete a folder, reorder placements, edit a placement's editorial title or copy, preview the public folder, a designated current folder, or any scheduler.

Multiple drafts: allowed. There is no uniqueness on number (SQL: nullable integer).

Current-folder rule (folders.js:pickCurrent, ordering from marketplace-db.js:getPublicFolders): live first, otherwise the newest open one, ordered by number descending (nulls last).

## 5. Data model and relationships

Definitions are from the SQL in the repo, not verified against the database.

| Entity | Storage | Key fields | Link to a folder |
|---|---|---|---|
| Folder | edits | number (int), title, standfirst, status, publish_at, published_at | n/a |
| Placement | edit_placements | edit_id, product_id (unique pair), position, editorial_title, editorial_copy, hero_image_id | Real foreign key. A product can sit in several folders. |
| Folder update | folder_updates | edit_id, body, image_path, position, published | Foreign key, on delete cascade |
| Market Note | notes ({id, data jsonb}) | status (draft / published), publishedAt, contentJson, websiteHtml, emailHtml | data.folderId: a loose reference with no foreign key. One folder per note. |
| Study / lookbook | studies (jsonb) | images[], captions[], coverImage | data.relatedDropId: loose reference. One folder per study. No status field. |
| Product (new) | products + product_images + product_variants | state (draft / submitted / accepted / declined / withdrawn), is_available, price_cents, proposed_price_cents | Through placements |
| Seller | suppliers, supplier_users, supplier_invites, profiles | type (consignor / brand / boutique / poda), commission_bps, status | n/a |
| Legacy item | items (jsonb) | status, dropNumber, closetOwner, ownerMinPayout, commissionPercent, privateNotes, pricing, soldActuals | dropNumber (a text number) |
| Legacy drop | drops (jsonb) | number (string such as "001"), status (In Assembly / Live / Archived) | Not connected to edits |
| Subscribers | subscribers (jsonb) | status, unsubscribeToken | n/a |
| Archive images | archive_images (jsonb) | n/a | None; no code path found that uses it publicly |
| Requests | None | Sell and Source forms are email only | n/a |

- Ordering: only placements and updates have a position, and the admin never changes it after creation.
- Folder delete: no function or UI exists. At the database level, placements and updates cascade. A note's or study's folderId is left pointing at nothing. The edit_placements.product_id link uses "on delete restrict", so products can't be deleted while placed.
- Naming drift: the same idea has several names. The admin calls folders "Edits", the old admin calls them "Drops", and the public site calls them "Folder 004". Numbering is also different in each place: an edits number is an integer, a legacy drops number is a string like "001", and notes and studies have their own issueNumber and studyNumber.

## 9. Fit with a folder-first admin

Already supports it:
- A folder record with status, number, standfirst and drop date.
- Product placements with a foreign key, and a seller approval pipeline feeding them.
- Published updates, and note and study attachment.
- Public read rules keyed to folder status.
- Placement editorial fields in the data layer and the public view.

Needs adjusting:
- Notes and studies live in a separate area of the admin. Adding them to a folder means attaching existing records. You cannot create a note or study from inside the folder.
- There is no concept of a "current" folder in the data. It is computed in the public JavaScript.
- Draft folders do not hide attached published notes, or any study (findings 3 and 4).
- Publishing is manual per piece. Notes, updates and the folder each have their own publish control.
- The legacy drops and items admin views still sit beside the new ones.

Would need to be added:
- Delete or archive-safely for folders, reordering, folder preview, upload in studies and updates, editing updates, and folder-level enforcement for notes and studies. Everything else above is wiring, not new capability.
